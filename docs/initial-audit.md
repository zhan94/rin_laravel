# RIN Laravel refinement audit

This is the initial read-only audit from 18 November 2026. Source references were made relative for repository use. They refer to the code as inspected at the time. Results after remediation are recorded in the [final acceptance report](final-acceptance.md).

**Audit date** 18 November 2026. **Decision** The current Laravel checkout is suitable for private engineering review. GitLab sharing should wait for the critical findings, dependency updates and confidentiality review. Remediation requires owner approval.

The audit compared the current Laravel checkout with the current custom OOP `rin` routes and workflows, its production readiness audit and its remediation report. The procedural `rin_legacy` project remains historical context. No maintained checkout files or records in either application database were changed. PHP, frontend and browser checks ran from a disposable Laravel copy using isolated SQLite and synthetic data. The prepared `rin_lara` was inspected with a MySQL-enforced read-only transaction. Security findings below distinguish a confirmed code path from a conditional exposure. No live attack testing was performed.

### Reference controls and intentional differences

The OOP report establishes changes R01–R14. Laravel already uses framework session/account lookup, cache-backed Fortify password login throttling, a debug flag, parameter-bound queries in the reviewed paths, private image uploads, transactions for catalog deletion, a public document root and content-hashed Vite entry points. Reviewed Laravel catalog deletes do not reproduce the OOP partial price-deletion path. CSS loaded through manually versioned static URLs and loose legacy assets remain exceptions to Vite-managed assets. Laravel does not contain the OOP per-request geolocation enrichment path. No equivalent to same-request raw password repopulation was found in the reviewed Laravel forms.

Vue/Inertia, Fortify/Sanctum, Eloquent and localized catalog titles remain the Laravel implementation. Different route URLs and the API envelope are intentional implementation differences. The old WebAuthn enrollment remains excluded by the prior migration policy. Driver redaction exists in reporting. The status meanings, role permissions, booking conflict and repeat-payment rules need explicit parity decisions where the current behaviors diverge. The absence of a verified equivalent in this audit does not establish that every remaining edge case differs.

Existing DTOs, repositories and transactions around booking, reports, issues, and notifications have practical value and should stay. Some thin paths, such as `UserService::paginate` and `roleOptions`, simply forward calls; this audit did not identify a performance or correctness benefit from a wholesale rewrite. Keep them until working on a related change shows a simpler dependency path that preserves tests and callers.

## Read-only database verification

MySQL 9.6.0 selected `rin_lara` on the Laravel default `mysql` connection. The transaction was read-only, with utf8mb4 and foreign-key checks enabled. There were **39 migration files and 39 matching ledger entries**, with no pending or missing migrations. Record counts included **10,000 customers, 39 locations, four cards, 12 card-price rows, 25,478 bookings, 55,111 booking-date links and 25,478 payment mirrors**.

All **26** physical foreign-key references were checked for orphans. The sampled logical customer, location/service and user/role relations also had zero missing parents. There were zero payment-mirror disagreements, zero negative or overpaid bookings, zero missing customer names/birth dates and zero nonempty duplicate customer-email groups. The scan found zero non-utf8mb4 text columns. The schema preserves the deliberate absence of a single foreign key for polymorphic booking service references and the global location sentinel. Existing application behavior should guide any additional database constraint.

## Remediation plan for approval

1. **Staff trust boundary and safe handoff.** Remove public staff enrollment, enforce reference action and target-role policies, close the hash fallback, align cookie/CSRF behavior, and unify account eligibility and revocation. Remove destructive default seeding from normal setup. Patch the PHP and frontend lockfiles on compatible lines and review the public screenshot inventory. Acceptance requires isolated positive and negative tests across all staff roles, credential changes, cookies, tokens, passkeys and serialization contexts.
2. **Close confirmed workflow gaps.** Wire the current dashboard to real data. Add safe report print/CSV handling and align the payment and booking retry/concurrency rules. Add security-event coverage, guard upload cleanup, and review the confirmed localized and mobile issues within the current UI. Acceptance requires real aggregates in a synthetic fixture, independent MySQL concurrency tests, normal browser workflows, German and English checks, and no changes to existing imported records.
3. **Prepare the repository for private review.** Repair the existing static-analysis gate, add a non-deploying GitLab pipeline retaining PHP 8.5, lint, static analysis, audits, tests and assets, and document a clean synthetic-data installation. Audit the exact Laravel history and review sensitive current assets, license provenance and third-party attributions. Document measured performance and intentionally different behavior. Any migration against the prepared database, history rewrite, licensing decision, push, merge or publication requires separate owner authorization.
