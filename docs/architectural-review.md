# Final architectural review

The review started at `610e9d3` and traced the staff, booking, catalog, seasons, reporting, notifications, issue, import, and dashboard paths. It used the [existing acceptance results](product-quality-review.md) for performance and browser coverage. The only production changes address duplicated visibility predicates and redundant dependency bindings in logs and notifications.

## Engineering principles

| Principle | Assessment and concrete evidence | Improvement and remaining limit |
| --- | --- | --- |
| KISS | The dashboard queries Eloquent and returns Inertia data directly. The booking write path coordinates several related records, so the service owns the transaction. The log service previously resolved the same role through two helpers to derive one visibility rule. [Dashboard controller](../app/Http/Controllers/DashboardController.php) · [Booking service](../app/Services/BookingService.php) | Log visibility now resolves the role once in a match expression. Customer and user pagination still forward through services. Removing those calls alone would add controller dependencies. |
| DRY | Booking validation and the availability views count the same `ServiceDate::activeBookingDates()` relationship. Vue uses shared date and EUR/BGN formatters. Logs repeated the record exclusion predicate, and notifications repeated the owner and deleted-record predicates. [Service date model](../app/Models/ServiceDate.php) · [Date formatting](../resources/js/modules/calendar/dateDisplay.ts) · [Currency formatting](../resources/js/modules/money/currency.ts) | A private Eloquent builder in each affected repository now defines the relevant visible rows. All matching operations reuse it. PHP money conversion and TypeScript display conversion serve different execution environments. |
| YAGNI | The log and notification interfaces mirrored one concrete repository each. Reference checks found those bindings only in the owning services and the container provider, with no alternative registration or test substitution. [Log service](../app/Services/LogService.php) · [Notification service](../app/Services/UserNotificationService.php) | Removed the two interfaces and their bindings. The prior cleanup removed unreachable frontend modules. Retained the legacy import command for its verified migration purpose. [Import operation](legacy-data-migration.md) |
| Single responsibility | Form Requests handle incoming shapes, Resources define serialized fields, and transaction services coordinate mutations. `ServiceBookingDateSynchronizer` handles date-level booking invariants. [Booking request](../app/Http/Requests/Api/V1/Bookings/StoreBookingRequest.php) · [Booking resource](../app/Http/Resources/Api/V1/Bookings/BookingResource.php) · [Date synchronizer](../app/Support/Bookings/ServiceBookingDateSynchronizer.php) | Services continue to decide access and transactions. Repositories build the visible reads and writes. `IssueService` still combines several closely related workflows, including private attachment cleanup when persistence fails. Splitting it would require tracing those transaction boundaries together. |
| Open/closed | Bonus, card, and equipment CRUD reuse actual shared transaction and notification behavior through a catalog trait. [Shared catalog operations](../app/Services/Concerns/ManagesCatalogCrud.php) · [Card service](../app/Services/CardCatalogService.php) | Kept the variation already used by those modules. The service-versus-bonus branch in booking persistence reflects the existing data model and its two write paths. |
| Liskov substitution | The booking repository tests exercise shared-location eligibility, booking-date synchronization, payment totals, and deactivation through the bound implementation. [Booking repository tests](../tests/Unit/BookingRepositoryTest.php) | The two affected services now depend on their tested concrete query classes. Evidence for the remaining interfaces is limited to the installed Eloquent implementations. |
| Interface segregation | Report queries have an identifiable read boundary. The booking interface covers aggregate persistence, date coordination, and payment synchronization, while each collaborator uses part of it. [Report contract](../app/Repositories/Contracts/Reports/ReportRepositoryInterface.php) · [Booking contract](../app/Repositories/Contracts/Bookings/BookingRepositoryInterface.php) | Removed the two mirrored interfaces. The remaining booking interface is relatively broad. New one-method contracts would add bindings for existing collaborators without simplifying the transaction. |
| Dependency inversion | Services receive dependencies through the Laravel container. Booking collaborators share a persistence contract, while log and notification repositories are stateless concrete dependencies. [Service bindings](../app/Providers/AppServiceProvider.php) | Concrete injection removes two manual bindings while preserving the service and query boundaries. Some other single-implementation contracts remain with their existing callers. [Laravel container resolution](https://laravel.com/docs/12.x/container#zero-configuration-resolution) |
| Clean code | The application uses PSR-4 namespaces, explicit DTOs, model casts, and typed service signatures. Legacy field names remain in the API and database mappings. [Booking DTO](../app/DTOs/Bookings/BookingData.php) · [Booking model](../app/Models/Booking.php) | Query builders have typed model annotations, and the new log role branch uses the existing enum. Booking and report Vue composables remain the largest frontend coordinators and already delegate focused work to modules. |

## Laravel framework choices

- **Eloquent and Collections** — The service schedule uses route-bound slots and relation counts. The date lookup stays scoped to its parent slot. The booking list eager-loads related records. The dashboard groups totals in SQL and maps its bounded daily rows for display. Report queries keep database-specific date and text behavior at the query boundary. [Schedule controller](../app/Http/Controllers/Api/V1/ServiceScheduleController.php) · [Booking queries](../app/Repositories/Eloquent/Bookings/BookingRepository.php) · [Report queries](../app/Repositories/Eloquent/Reports/ReportRepository.php) · [Eloquent relationship counts](https://laravel.com/docs/12.x/eloquent-relationships#counting-related-models)
- **HTTP contracts and authorization** — Form Requests, Fortify, Sanctum, staff-account middleware, and policies handle input, session eligibility, and roles. Account writes reauthorize against rows loaded under lock. API Resources and the shared exception handler preserve envelopes and machine-readable errors. Booking routes retain explicit lookups where callers depend on domain-specific error codes. [API routes](../routes/api.php) · [User policy](../app/Policies/UserPolicy.php) · [User service](../app/Services/UserService.php) · [Exception and middleware registration](../bootstrap/app.php)
- **Transactions and events** — Service and season writes coordinate with booking capacity on the service row. Booking and payment writes use persisted receipts for supported retries and hold the relevant locks while synchronizing dates or balances. The booking confirmation listener runs after commit. [Slot service](../app/Services/ServiceSlotService.php) · [Payment service](../app/Services/BookingPaymentService.php) · [Mutation receipt](../app/Support/Bookings/BookingMutationReceipt.php) · [After-commit listener](../app/Listeners/SendBookingEmail.php) · [Laravel transactions](https://laravel.com/docs/12.x/database#database-transactions)
- **Schema and tests** — Migrations define the schema and constraints. The guarded demo seeder uses the existing services for bookings and periods. Feature tests use factories and `RefreshDatabase` on isolated in-memory SQLite. The separate race harness uses independent MySQL processes because SQLite tests provide different concurrency evidence. [Migrations](../database/migrations/) · [Demo seeder](../database/seeders/DemoDatabaseSeeder.php) · [Database test guard](../tests/TestCase.php) · [MySQL race harness](../scripts/verify-mysql-concurrency.php)

## Scope and unresolved trade-offs

- The log service still owns the roles and their visibility. Its repository applies a single exclusion filter to listing and all delete paths. The notification repository applies the same owner and deleted-record filter to listing, unread count, lookup, and mark-all. The services retain their existing error handling and notification transaction boundaries. [Log scenarios](../tests/Feature/Api/V1/Logs/LogApiTest.php) · [Notification scenarios](../tests/Feature/Api/V1/Notifications/NotificationApiTest.php)
- Legacy booking types and shared pickup sentinels still require application-level checks beyond ordinary foreign keys. Offset pagination and substring search have measured cost. Whole-result report export still assembles pages in the browser. The recorded 100,000-customer benchmark covers repository calls for list and search. [Schema and mapping](legacy-data-migration.md) · [Performance measurements](product-quality-review.md#performance)
- Private database credentials and records belong in their original environment. The review and verification use the standalone synthetic application. Publication clearance and hosted CI are tracked in the [release handover](publication-readiness.md).
